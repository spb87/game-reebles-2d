# Project conventions

Coding standards and naming conventions for this project. All agents must follow these. Updated by the Architect.

Stack layers: **Unity C#** (game code in `game/Assets/`) and **Python tooling** (art pipeline in `art/tools/`, repo helpers in `tools/` — stdlib only). Both have testing conventions defined below.

## File naming

- C# scripts: `PascalCase.cs`, filename must match the primary class name (Unity requirement)
- MonoBehaviour scripts live under `game/Assets/Scripts/{Player,NPC,Quests,UI,Core}/`
- Editor-only scripts (scene builders, build scripts): `game/Assets/Editor/`
- Scenes: `PascalCase.unity` under `game/Assets/Scenes/` — **generated, never hand-edited** (see "Scene generation" below)
- Prefabs: `PascalCase.prefab` under `game/Assets/Prefabs/` — generated by scene builders
- Quest data: `kebab-case.json` under `game/Assets/Data/Quests/` (DEC-6)
- Sprites/art in the build: `game/Assets/Art/{Sprites,Backdrops,Sheets}/` — committed, they are game assets
- Assembly definitions: `Reebles2D.<Area>.asmdef` (e.g., `Reebles2D.Player.asmdef`) — one per folder that grows past ~5 scripts
- Tests: `game/Assets/Tests/EditMode/` and `game/Assets/Tests/PlayMode/`, each with its own asmdef; test classes named `<ClassUnderTest>Tests.cs`
- Python tools: `snake_case.py` under `art/tools/` and `tools/`
- Art staging: `art/staging/` (gitignored — regenerable intermediates); per-asset prompt records in `art/prompts/<asset-name>.md` (committed)

## Code style

- C#: Unity conventions — `PascalCase` for types, methods, public members, constants; `camelCase` for private fields including `[SerializeField]` fields (e.g., `[SerializeField] private float moveSpeed`)
- Braces on new lines (Allman), 4-space indent — Unity default
- Block-scoped namespaces (`namespace Reebles2D.Player { ... }`) — file-scoped namespaces are unavailable (C# 9)
- No regions unless wrapping a large serialized-fields block
- Formatter/linter: `.editorconfig` at repo root is the source of truth; no enforced CLI linter — Unity's compiler warnings must be clean
- Python: PEP 8, snake_case, type hints where practical, **stdlib only**

## Documentation standard

- C#: XML doc comments (`/// <summary>`) on public classes and public methods. Internal helpers get a comment only when logic is non-obvious
- Python: one module docstring per script (what it does, usage, expected output path)
- No comment noise — match surrounding density

## Testing expectations

### Unity (game code)

- Framework: **Unity Test Framework** (`com.unity.test-framework`) — EditMode + PlayMode
- EditMode tests: required for every pure C# class (movement math, quest state transitions, carry-slot logic, JSON quest parsing). These must not depend on a loaded scene
- PlayMode tests: required for behaviors that need a running scene (player moves on input, interact prompt appears in radius, pickup fills carry slot, fence blocks movement)
- Running tests: Unity Test Runner in Editor, or batch mode:
  `Unity.exe -batchmode -projectPath game -runTests -testPlatform EditMode -testResults results.xml`
- Coverage target: no formal target — every task's exit criteria must name its verification
- Test location: `game/Assets/Tests/EditMode/`, `game/Assets/Tests/PlayMode/`
- Mocking: n/a — keep logic pure so mocks are unnecessary

### Art pipeline (Python tooling)

- `gen_image.py` and helpers: stdlib-only so they run on any stock Python; verification is a real generation call producing a file (cheap — pennies)
- Sprite-import contract: promoted sprites are committed under `game/Assets/Art/` **with** a prompt record in `art/prompts/<asset>.md` (model + full prompt incl. style anchor) so any asset can be regenerated
- Staging outputs in `art/staging/` are gitignored — only promoted, game-ready assets enter `game/Assets/`

### Shared

- TDD approach: test-after for simple Unity behaviors, TDD encouraged for pure logic (quest state machine, carry slot)
- Assertion style: happy path required; include at least one edge/bounds assertion where the logic has a boundary (e.g., interaction radius edge, delivering with empty carry slot)

## Dependency injection and testability

- DI pattern: manual — no framework. Wire dependencies via `[SerializeField]` fields assigned in the Inspector (or by scene-builder code), or `GetComponent` in `Awake`
- Testability rule: put tunable math and decision logic in plain C# classes (non-MonoBehaviour) so EditMode tests can instantiate them; keep MonoBehaviours thin (input reading, physics calls, inspector wiring)
- I/O separation: `UnityEngine.*` calls stay inside MonoBehaviours; pure helpers take/return values

## Scene generation

- Scenes and prefabs are **generated by editor scripts**, not hand-authored YAML: `game/Assets/Editor/VillageSceneBuilder.cs` is the single entry point that regenerates `Village.unity` and its prefabs atomically
  `Unity.exe -batchmode -nographics -projectPath game -executeMethod Reebles2D.Editor.VillageSceneBuilder.Build`
- Any new placed-entity or scene-generation step folds into the builder — separate ordered steps are the ordering trap this convention exists to prevent (carried over from the 3D project)
- Hand edits to `.unity`/`.prefab` YAML will be overwritten on the next regen — treat them as build artifacts with a committed generator

## Git conventions

- Commit messages: conventional commits (`feat:`, `fix:`, `refactor:`, `test:`, `chore:`, `docs:`), reference the task where one exists: `feat(TASK-4): add player movement`
- One commit per task by default; a task may split into logical commits
- `.ai/` bookkeeping commits use `docs(ai): ...` (orchestrator only)
- Never commit: `game/Library/`, `game/Temp/`, `game/Obj/`, `game/Builds/`, `game/Logs/`, `*.csproj`, `*.sln`, `.devin/mcp_config.local.json`, `.env`, `art/staging/`

## Component patterns

- MonoBehaviours are thin shells: read input → call pure logic → apply to `Rigidbody2D`/transform
- All game-feel tunables (speeds, interaction radius, camera damping) are `[SerializeField]` fields visible in the Inspector — hard requirement from the scope doc (design for fast tuning loops)
- Movement: kinematic `Rigidbody2D` + `MovePosition` in `FixedUpdate` (DEC-4) — no CharacterController (3D-only), no dynamic physics pushing
- Prefab discipline: every placed entity (Reeble, NPC, building door, pickup, fence segment) is a prefab; scenes contain prefab instances, not raw GameObjects
- UI: uGUI Canvas, screen-space overlay, anchored corners; mobile on-screen joystick + interact button feed the same Input System action map

## API conventions

- RouteLLM image API via `art/tools/gen_image.py` — no other network calls in the project
- In-game: no backend, no network APIs in v1

## Environment and configuration

- `.env` at repo root holds `ROUTELLM_API_KEY` — gitignored, never committed; `.env.example` committed with a placeholder
- Machine-local MCP config: `.devin/mcp_config.local.json` (auto-gitignored — never commit it)
- Unity project settings live in `game/ProjectSettings/` (committed)

## Dependency management

- Unity packages: `game/Packages/manifest.json` — committed, versions pinned by Unity
- Unity Editor version: pinned in `game/ProjectSettings/ProjectVersion.txt` (`6000.3.24f1`) — do not upgrade without a DEC
- Python: no package manager — all scripts are stdlib-only by design
- Global installs: never install project dependencies globally

## Devin conventions

When using Devin (CLI or Desktop), follow these additional conventions:

### DeepWiki usage

- DeepWiki auto-generates architecture documentation from the codebase.
- Use DeepWiki as the first source for understanding code structure before reading source files manually.
- Update `.devin/wiki.json` when adding major new modules or components to ensure DeepWiki documents them.
- DeepWiki supplements but does not replace `.ai/memory/decisions.md` — decision rationale still belongs in decisions.md.

### Spaces

- Create a Space for each feature or milestone to provide context isolation.
- All agents working on a feature should operate within the same Space to share Git worktree context.
- Spaces do not sync across team members — coordination happens via Jira or `.ai/` files.
- When a milestone completes, archive the Space and create a new one for the next milestone.

### Fast Context

- Use Fast Context queries in natural language to retrieve relevant code sections.
- Do not manually crawl directories when Fast Context can surface the information.
- Fast Context retrieves code but does not grant file permissions — always respect task "Files allowed" constraints.
